NOK Inc WordPress / Elementor → Next.js Migration Runbook
Developer Execution Guide
Goal: reproduce the current nokinc.com visual design in a clean Next.js codebase, deploy it to OCI, switch DNS, and retire WordPress safely.


Independent Architecture Decision
For this site, the cleanest approach is not to convert Elementor-generated HTML into React. Use the existing site as a visual and content specification, rebuild the UI as reusable Next.js components, and prove parity with automated screenshots. This avoids carrying Elementor markup, plugin dependencies, and WordPress runtime risk into the new application.
Do not use an “Elementor-to-React converter” as the production implementation.
Do not deploy Kubernetes/OKE for this site unless there is a future workload that actually requires orchestration; OCI Container Instances are simpler for a single web container.
Do not delete WordPress on DNS cutover day. Retire it only after the new site is verified and the rollback window has passed.

Definition of Done
☐ Every current public URL either remains exactly the same or has an intentional 301 redirect.
☐ Desktop, tablet, and mobile pages visually match the approved WordPress baselines.
☐ No page depends on WordPress, Elementor, wp-json, wp-content URLs, or WordPress plugins at runtime.
☐ All images, fonts, icons, and documents required by the site are owned and served by the new application or an approved external service.
☐ Navigation, forms, links, responsive behavior, SEO metadata, social metadata, robots.txt, and sitemap are verified.
☐ Production build, container health check, OCI deployment, TLS, and DNS are tested before WordPress is retired.

10. Phase 9 — Deploy to OCI
Recommended simple production topology: public OCI Load Balancer → private OCI Container Instance running the Nginx/Next.js static container. Store the image in OCI Container Registry (OCIR). OCI documents Container Instances as a serverless container service suitable when Kubernetes orchestration is not required.
10.1 Push the image to OCIR

Use immutable image tags such as the Git commit SHA. Do not deploy production from a mutable “latest” tag.
10.2 Create the OCI Container Instance
Create or reuse a VCN with a public subnet for the load balancer and a private subnet for the container instance.
Ensure the private subnet can reach OCIR. OCI documentation recommends a Service Gateway when pulling OCIR images from a private subnet.
Create the Container Instance from the OCIR image and expose container port 8080.
Allow inbound TCP 8080 only from the load balancer subnet/security group, not from the public internet.
Confirm the container is running and /health returns HTTP 200 from within the network path.
10.3 Create the public Load Balancer
Create an OCI Load Balancer in the public subnet.
Create a backend set pointing to the Container Instance private IP on port 8080.
Configure the backend health check path as /health.
Create an HTTPS listener on port 443 and attach a CA-issued certificate for nokinc.com / www.nokinc.com. Optionally redirect HTTP 80 to HTTPS.
Test through the load balancer public IP/temporary hostname before touching DNS.
10.4 DNS cutover
At least a day before cutover, lower the existing DNS TTL to approximately 300 seconds if your DNS provider permits it.
Create a staging hostname such as next.nokinc.com pointing to the new OCI load balancer and perform final acceptance testing.
Record the current WordPress DNS values so rollback is one edit, not an investigation.
Change the nokinc.com/www records to the OCI load balancer public IP or provider-supported target.
Verify from an incognito browser and a separate network/mobile connection.
Keep WordPress intact during the rollback window. Only decommission it after logs, forms, analytics, and page checks are clean.
11. Phase 10 — Minimal CI/CD After the First Manual Deployment
The junior developer should complete one manual deployment first so the infrastructure is understood. Then automate the exact same steps.

Add OCIR login/push and OCI deployment only after the manual path works. Store OCI credentials or workload identity values in GitHub environments/secrets; never commit them to the repository.
12. How to Find and Correct Old Placeholder Content in WordPress
12.1 Important correction about the earlier “Lorem ipsum” report
Your Ctrl+F result is meaningful. The web source I previously used for the homepage is a crawler snapshot marked as approximately seven months old, not a guaranteed live copy of what your browser is rendering today. Therefore, do not send the junior developer hunting the current homepage solely because that old crawl contained “Lorem ipsum.” The correct source of truth is the current WordPress database/editor plus the current live browser.
A more recent indexed result (approximately five months old) still shows Lorem ipsum on the Electric Tricycles page, and the older Software Solutions crawl also contains Lorem ipsum. These are leads to verify, not proof that the text remains live today.
12.2 Definitive method #1 — Search the WordPress database with WP-CLI
If the host provides WP-CLI, this is the fastest definitive search because Elementor page content is commonly stored in WordPress post metadata rather than as simple visible page text.

WP-CLI reports the table, column, row/primary key, and nearby match. Elementor content often appears in wp_postmeta (frequently in _elementor_data). Do not manually edit serialized Elementor JSON in the database. Use the match to identify the page/template, then edit it through Elementor.
12.3 Map an Elementor post ID back to the page/template
If the database result identifies a post_id, map it to the WordPress title before editing. Replace wp_ with your actual database prefix if different.

12.4 Definitive method #2 — Elementor Structure/Navigator
WP Admin → Pages → choose the page → Edit with Elementor.
Open Elementor Structure/Navigator with Ctrl+I (or click the Structure icon). Elementor documents this view as the page tree and specifically recommends it for accessing hidden/overlapped elements.
Expand every container/section and inspect Heading, Text Editor, Counter, Icon List, HTML, and template widgets. Structure can reach elements hidden behind z-index, negative margins, or absolute positioning.
Switch the editor to Desktop, Tablet, and Mobile. Check Advanced → Responsive on containers/widgets if content appears only at a specific breakpoint.
Replace placeholder text in the correct widget, click Update, then verify in an incognito browser.
12.5 Check Theme Builder and global templates
Placeholder text in a header/footer/global section may not belong to the current page. Use Elementor Finder (Ctrl+E) to jump to pages/templates/settings, and inspect Templates / Theme Builder for Header, Footer, Single Page, Archive, and saved sections. Confirm each template’s display conditions.
12.6 If WP-CLI is unavailable — use phpMyAdmin search
Open phpMyAdmin from the hosting panel and select the WordPress database.
Use the database Search tab and search for “Lorem ipsum” across all tables.
Note the matching table, record ID, and post_id. Elementor content is often in wp_postmeta.
Map that post_id to wp_posts.ID to get the page/template title.
Edit the page/template in WordPress/Elementor; do not directly rewrite Elementor JSON in phpMyAdmin unless you are deliberately performing a backed-up, tested database operation.
12.7 Clear Elementor and site cache after corrections
Elementor’s current documentation says to use WP Admin → Elementor → Editor → Tools → Clear Files & Data after design/content changes when cached files may be stale. Also purge any hosting/cache plugin/CDN cache, then verify in a private/incognito browser.

13. Final Acceptance and WordPress Retirement Checklist
☐ Run npm run lint and npm run build with zero errors.
☐ Run all Playwright visual tests against the production-style build, not only next dev.
☐ Check every URL from urls.txt for HTTP 200 or an intentional redirect.
☐ Search the new repository and rendered HTML for wordpress, wp-content, wp-json, elementor, and old WordPress hostnames; there should be no required runtime dependency.
☐ Test desktop, tablet, and phone navigation on real browsers/devices.
☐ Submit every form and confirm receipt/processing.
☐ Verify TLS certificate, HTTPS redirect, canonical URLs, sitemap.xml, robots.txt, and analytics.
☐ Verify OCI load balancer health checks and container restart behavior.
☐ Keep the WordPress backup and old DNS values documented.
☐ After the agreed rollback window, disable WordPress public traffic, archive the final backup, and then cancel/retire the WordPress hosting.
14. Independent Review of This Plan

Decision: this is the recommended execution plan for a junior developer because it teaches the migration process, preserves the current look, avoids WordPress technical debt, and keeps OCI deployment understandable without introducing infrastructure that the site does not need.
